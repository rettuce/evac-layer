# EVAC LAYER app (renderer, admin, dashboard)

Nuxt 4 SPA. Screens render offline: fonts are bundled, layouts come from `data/` through the app's own API.

## Development

```sh
pnpm install
pnpm -F app dev            # http://127.0.0.1:3150
node scripts/shot.mjs      # five shapes at native size into app/shots/ (pillar at half scale)
```

## Tests

```sh
pnpm -F app test   # nuxt build, then node --test app/test/*.test.ts (no extra dependencies)
```

`test/policies.test.ts` covers the pure rules (dev layout bridge paths, trusted `src`, admin access, the live approval gate); `test/server.test.ts` starts the production build twice on a free port with a temporary data directory and checks the gate, the admin refusals and the token mode end to end; `test/delivery.test.ts` checks the feed (ambient before approval, alert with layouts and assets after, ETag, schema check through `pnpm -F agents validate`) and a signed webhook delivered to a local receiver; `test/notify.test.ts` checks which states are notified, the notice text, when a channel sends and the SMTP options, and `test/notify-server.test.ts` the notices sent by the production build to a local Slack receiver and a local SMTP receiver; `test/liveness.test.ts` and `test/liveness-server.test.ts` do the same for the notices that receiving or a screen's feed requests have stopped; `test/ambient.test.ts` covers the hourly ambient pick.

## Production build

```sh
pnpm -F app build
HOST=127.0.0.1 PORT=3160 node app/.output/server/index.mjs
```

| URL | What it shows |
|---|---|
| `/screen?shape=16x9&mode=live&site=<site id>` | what the site shows now: its recorded `replay` (window and speed from the site file), or, without `replay`, the bulletin last posted to `/api/admin/live` |
| `/screen?shape=16x9&mode=live&municipality=05210&speed=1200` | the pre-site form: replays the record of the municipality's only site with the window and speed of the query (`&clock=virtual&t=<ms>` for frame-exact recording) |
| `/screen?shape=16x9&layout=<fixture>` | a fixture from `app/fixtures/` (a production `/screen` without `layout` or `src` says the layout is unspecified instead of showing a fixture) |
| `/admin` | bulletins per site, previews for every shape, Verifier result, approval and per-site auto publish |
| `/dashboard` | totals over `data/` (`?clock=virtual&t=<ms>` for the count-up) |

`app/layout/README.md` lists every `/screen` parameter and the data attributes a recorder or Verifier can wait on.

### Sites

A site is one screen location: `data/sites/<site_id>.json` (`schema/site.schema.json`; the file name is the `id`). Its screens live in `data/layouts/<site_id>/` (`index.json` and `<bulletin_id>/<shape>.json`), and approvals are keyed `<site_id>/<bulletin_id>`, so two sites in one municipality never share an approval. APIs take `site` (`site_id` in POST bodies). `municipality` alone still works as an alias when the municipality has exactly one site; with none or several the API answers 400 and asks for `site`. An approval key written before sites (`<municipality>/<bulletin>`) is read as that only site, and ignored with a warning when the municipality has several. On a server without facility tokens, the server rewrites at startup each such key whose municipality has exactly one site to `<site_id>/<bulletin>` in `data/approvals.json`, so that a site registered later in the municipality does not change whose approval it is. On a server with facility tokens (or a token ledger it cannot read) old keys are neither rewritten nor read as any site's approval, by the server or by `pnpm -F agents export`, and stay in the file as they are.

A site file that cannot be read or is not valid JSON is skipped with one warning, so it does not stop the catalog or the approvals of the other sites.

### Sites over HTTP

Admin access as below; a facility token acts on its own sites only. Errors carry `data.code` (`invalid-request`, `not-found`, `site-id-taken`, `geocoder-unavailable`, and for generations `generation-running`, `generation-rate-limited`, `municipality-not-prepared`, `generation-disabled`, `site-busy`, and for class approvals `too-many-sites`).

- `PUT /api/admin/sites/<site_id>` `{lat, lng, facing_deg?, name?, municipality_id?, actor?}`: registers the site (201) or updates its place (200). The id follows `schema/site.schema.json` (3-64 of `a-z 0-9 -`); a new id of five digits only is refused, because it would read as a municipality in an old approval key, and an id that differs from an existing site only in case answers 409 `site-id-taken`. `municipality_id` comes from the GSI reverse geocoder unless given (a given code that differs is kept and reported in `warnings`; without it, a geocoder that does not answer gives 502 `geocoder-unavailable`, and a point in no municipality, at sea or outside Japan, 400 `invalid-request`). The geocoder is not asked when `lat` and `lng` equal the stored ones, and is asked one request at a time. A site created with a facility token carries that token's `facility_id`; an id already used by another facility's site, or by a site without `facility_id`, answers 409 `site-id-taken` to a facility. The operator keeps an existing site's `facility_id` and creates sites without one (assign it with `pnpm -F agents site --facility`). Fields the body leaves out (`name`, `note`, `replay`) are kept, except `facing_deg`, which is part of the place: a body without it removes a stored one (the screens then show a north-fixed compass arrow); the same body twice changes nothing, and a change of `lat`, `lng`, `facing_deg` (including gaining or losing it) or `municipality_id` stamps `location_updated_at` (so does `pnpm -F agents site --force`). `NUXT_REVERSE_GEOCODER_URL` points the lookup elsewhere (tests). Registering an id that has no site file removes whatever is still stored under it (approvals, screens, live state, exports, webhook registrations), so a new site never starts with an earlier one's approvals.
- `GET /api/admin/sites/<site_id>` and `GET /api/admin/sites` (`?facility_id=` narrows the operator's list) answer the site state: the stored `site`, `facility_id` (or null), `auto_publish`, `municipality_prepared` (`data/municipalities/<code>.json` exists), `needs_generation` (false while a generation job is queued or running; otherwise true when the site has no screens, when the last finished job failed, or when a class `generate` composes (the `composable` list in `generation.json`) failed in the last job, has no screen or is `stale`; a stale class it cannot compose (flood, tsunami for now) does not count, and before any job has a result every stale class does), `last_generation` (the latest generation job, below), `classes` (one per `<hazard>/<template>/<level>`, standing for the bulletin the last job composed for the class, or else the newest screen of the class: `bulletin_id`, `synthetic` (the id starts with `SYN-`), `digest`, `outcome` `pass`/`fail` from its report or `pending` without one, `stale` (the screens may be of an earlier place: a job's screens when the site's `municipality_id`, `lat`, `lng` or `facing_deg` differ from when that job started, any other screen when its layout files are older than `location_updated_at`), `unchanged` (the same bulletin with the same digest as when the latest job started, so an approval given before it still holds; left out while the latest job has not started), `approved` as in the catalog, `approved_via` (`bulletin` or `class`, while `approved`), `approved_at`, `approved_by {token_label, mode, actor?}` (the credential's label, `operator` for the operator token; `mode` `reviewed` when the approval named the digest of the screens, `bulk` when it did not; left out for approvals recorded before it was kept), `live`, `previews` (the preview URL per shape, for the shapes whose PNG was rendered from the current screens)), `approved_classes {approved, total}`, `exports {pending, failed}` from `data/live/<site_id>.export.json`, and `warnings`.
- `DELETE /api/admin/sites/<site_id>` (204) removes the site's screens, reports, approvals, live, receiver, export and notice state, `dist/<site_id>/` and webhook registrations, and the site file last. Its feed answers 404 from then on; webhook retries to its registrations stop, and an export that was running when it was deleted leaves no files or record. A generation job of the site that is queued never runs, one that is running is stopped (its whole process group) before anything is removed, and the job record and previews are removed with the rest.
- `POST /api/admin/sites/<site_id>/generations` `{actor?}` (202, `Location` header) queues a generation job: the server runs `pnpm -s -F agents generate --site=<id> --writer=<w> --verifier=<v> --base-url=<this server>` (`NUXT_GENERATE_COMMAND`, `off` answers 503 `generation-disabled`; `NUXT_GENERATE_WRITER` default `live`, `NUXT_GENERATE_VERIFIER` default `browser`), then renders a preview PNG of every shape of each class that passed, with `pnpm -s -F agents preview` (`NUXT_PREVIEW_COMMAND`, `off` skips previews). Jobs run one at a time over all sites. A site with a job queued or running answers 409 `generation-running` with its `generation_id`; a site whose municipality is not prepared, 409 `municipality-not-prepared`. A facility may start 6 jobs an hour over all its sites (the operator 6 per site; `NUXT_GENERATIONS_PER_HOUR` changes it) and have 2 unfinished at a time (`NUXT_GENERATION_OPEN_JOBS_PER_FACILITY`), counted in the server process; past either, 429 `generation-rate-limited` with `Retry-After`. A job has 90 minutes for composing and previews together. The answer is the job: `generation_id`, `site_id`, `status` `queued`, `created_at`, `classes: []`, `started_by {token_label, actor?}` (`operator` for the operator token).
- `GET /api/admin/sites/<site_id>/generations/<generation_id>` answers the job: `status` `queued` → `running` → `done` or `failed`, `started_at`, `finished_at`, and `classes` copied from `data/layouts/<site_id>/generation.json` (`class`, `bulletin_id`, `synthetic`, `outcome`, `reason`, and `preview_error` when a preview could not be rendered, which does not fail the job). A job is `done` only when the command exits 0 and wrote a `generation.json` for this run; otherwise it is `failed` with `error_code` `generate-failed`, `timed-out`, `no-result`, `server-restarted` or `internal-error` and a fixed `error` text. The command's output goes to the server log only, and a class `reason` is cut to 300 characters with paths, URLs and `NAME=value` pairs left out. The latest job and the one before it stay readable. Stopping the server stops the running command (SIGTERM to its process group, SIGKILL after 5 s, then the Chrome it wrote to the pid file the server named, once that pid leads its own process group and descends from the command); a server killed outright stops a child (of a job or of an export) it left on the next start, once `ps` shows the recorded process group, or its members when the leader is gone, started at the recorded time with the job's arguments. A group that started at another time or runs another command is someone else's and is left alone. A child that cannot be checked or does not stop goes to `data/orphans.json`, which a DELETE of the site does not clear: until it ends, its site takes no job (409 `generation-running`) and its id no new registration (409 `site-busy` to the operator and to the facility that owned the site, `site-id-taken` to any other facility). The check needs a `ps` that knows `-A` and `lstart` (procps or BSD); with another one (busybox, for one) nothing can be checked, so nothing is stopped after a restart and the sites concerned answer 409 until their processes end.
- `GET /api/admin/sites/<site_id>/previews/<bulletin_id>/<shape>.png` answers a preview PNG with `ETag` set to the layout digest it was rendered from and `Cache-Control: no-store`, while that digest is still the bulletin's; otherwise 404. Synthetic and unapproved real bulletins alike: a preview is for the person who approves, never for delivery. A bulletin is rendered again by the next job until every shape it has a layout for has a PNG (`preview_error` `preview-failed`, `timed-out` or `screens-changed` on the job's class until then), previews of bulletins that no longer stand for a class are removed at the end of each job, and nothing under `data/previews/` is read or written through a symbolic link.
- `GET /api/admin/classes` answers `{classes}`: one row per class of the facility's sites (drill and test classes left out), `class`, `total`, `approved` (sites whose class approval holds for the screens that stand for the class now), `pending` (sites a bulk approval would approve: no reason to skip them and no such class approval yet), `blocked {count, reasons}` (sites with screens a bulk approval would skip, and the reasons), `live` (a site of the facility is showing a bulletin of the class) and `sites [{site_id, state}]`, where `state` is the class's entry of `GET /api/admin/sites/<site_id>`. `total` is `approved + pending + blocked`; a site without screens of the class is not counted, and a site whose bulletin approval alone lets the class out counts as `pending` or `blocked`. A facility token gets its own facility whatever `facility_id` it sends; the operator must send `?facility_id=` (400 otherwise). Sites are read 8 at a time.
- `POST /api/admin/class-approvals` `{class, approved, site_ids?, facility_id?, actor?}` approves (`approved: true`) or revokes a class at every site of the facility, or at the sites in `site_ids`. Either way at most 200 sites (`site_ids` counted before duplicates are dropped); more answers 400 `too-many-sites`, and a larger facility is sent in several requests with `site_ids`. Approving writes only the class approval (`classes["<site_id>/<class>"]` with `approved_from` the bulletin that stands for the class at the site, `mode: bulk`, `token_label`, `actor`), never a bulletin approval: nobody looked at the screens, so the delivery gate still asks each bulletin it opens for the browser check, the headline evidence (with the reviewed ja_easy table) and the class digest. The same class approval already in place is left as it is. The class is judged, then read and judged again under the site's lock, and written only when the same bulletin and screens still stand for it; the site's exports are then requested. Revoking sets the site's class approval to `approved: false` (recording `mode`, `token_label` and `actor`), whichever bulletin it was approved from, and leaves bulletin approvals alone; `bulletin_approvals_left` lists the bulletins of the class whose own approval still lets them out. The answer is `{class, results: [{site_id, result, reason?, bulletin_approvals_left?, state?}]}` with `result` `approved`, `revoked` or `skipped` and `state` the class state after the request (a site deleted or registered again meanwhile answers `not-found`). A site is skipped, and the others still processed, with `reason` `not-found` (no such site, a site of another facility, or with the operator's `facility_id` a site outside that facility; they answer alike), `no-screens`, `not-passed` (the screens did not pass the browser check of every shape, or the report is not of these layout files), `stale` (the screens may be of an earlier place), `headline-unchecked` (no evidence that the headline is the JMA dictionary table's; the review of the ja_easy table is not asked here), `draft-wording` (the last Writer attempt in the report was the placeholder), `wording-unknown` (the report names no Writer source known to be real wording: `writer-cache`, `writer-class-cache:…` or `writer-api:…`), `changed` (another bulletin or other screens stood for the class by the time of the write) or, when revoking, `not-approved`. A drill or test class, a `class` that is not `<hazard>/<template>/<level>`, a malformed or empty `site_ids`, an unknown field, an `actor` whose `id` or `name` holds a control character, or the operator with neither `facility_id` nor `site_ids` answers 400 `invalid-request`. The audit line of the request carries `class_approvals {class, approved, results: {approved, revoked, skipped}}`.

The commands the server starts get these names of its environment and no others: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `TMP`, `TEMP`, `LANG`, `LANGUAGE`, `TZ`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`, `LC_COLLATE`, `LC_NUMERIC`, `LC_TIME`, `LC_MONETARY`, `CHROME_PATH`, `EVAC_RAW_DIR`, `EVAC_URL`, `JMA_FEED_DIR`, `JMA_SAMPLES_DIR`, and for `generate` only `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and `NODE_EXTRA_CA_CERTS`; the server sets `EVAC_DATA_DIR` and `EVAC_CHROME_PID_FILE`. Nothing named `NUXT_*` reaches them. A failed export's reason (in the export record and in `exports.failed`) is cut to 300 characters with paths, URLs and `NAME=value` pairs left out; the whole output goes to the server log. The browser check of `generate` (`NUXT_GENERATE_VERIFIER=browser`) works against this server, production build included: the page it opens asks for `/api/admin/preview-layout?verifier=<hash of the layout>`, and Chrome answers that request from the layout being checked, so the request never reaches the server and needs no admin credential.

Every write keyed by a site (its file, approvals, auto publish, live state, webhook registrations, export records) runs under one lock per site and checks under it that the caller may still act on the site, so a site deleted and registered again by another facility never receives a write meant for the old one.

### Audit

Every admin request that changes something (any method but GET, HEAD and OPTIONS) appends one line to `data/audit.jsonl` (gitignored): `at`, `method`, `path`, `site_id` when known, `principal` (`{kind: "operator"}` or `{kind: "facility", facility_id, label}`), `actor` when given, and the answer's `status`, refusals included. A request refused for want of a credential is not recorded. Past 10 MB the file moves to `audit.jsonl.1`, and five older files are kept (`NUXT_AUDIT_MAX_BYTES` lowers the limit for tests). `actor {id, name?}` (each up to 120 characters) comes from the body, or for a request without one from `X-EvacLayer-Actor-Id` and `X-EvacLayer-Actor-Name` (percent-encoded UTF-8); a malformed one answers 400. It is recorded, not verified.

### Data directory

The server reads `data/layouts`, `data/reports`, `data/sites` and `data/municipalities`, and writes only `data/sites/<site_id>.json` (through `PUT /api/admin/sites`), `data/audit.jsonl`, `data/approvals.json` (approval and auto-publish state; a missing file means nothing is approved), `data/subscriptions.json` (webhook registrations with their secrets and the last state each was sent, mode 600), `data/live/<site_id>.json` (the live state), `data/live/<site_id>.export.json` (the outcome of the last export of each bulletin the server started), `data/live/<site_id>.generation.json` (the latest generation job and the one before it), `data/live/<site_id>.notify.json`, `data/live/notify/receivers.json` and `data/live/notify/feed-idle.json` (the operator notices sent, below), `data/live/<site_id>.feed-seen.json` (when the site's screen last came, below) and, through the preview command, `data/previews/<site_id>/<bulletin_id>/` (preview PNGs and the layout digest they show; nothing serves this directory but the preview path above). Delivery assets (PNG/HTML from `pnpm -F agents export`) are read from `dist/` (`NUXT_DIST_DIR` to move it). When an approval lets bulletins go out, the server runs that export itself for each one whose current screens are not exported yet, one at a time in the background (and every five seconds for the bulletin a publishing site is showing without `assets`), and so writes to `dist/` through it (`NUXT_EXPORT_COMMAND`, default `pnpm -s -F agents export`; `off` disables it). The feed links exported files only while `layout.digest` beside them matches the layout files being served.
`EVAC_DATA_DIR` moves the data directory (shared with `agents`; `NUXT_DATA_DIR` is kept as an alias). The repository root is fixed at build time; when the build runs from another location, point it at the repository too:

```sh
NUXT_REPO_ROOT=/path/to/evac-layer EVAC_DATA_DIR=/path/to/evac-layer/data node app/.output/server/index.mjs
```

### What stays development-only

- `/api/layout?file=<absolute path>` (renders any JSON file inside the repository; nothing in the repository uses it any more) returns 404 in a production build.
- `/screen?src=` accepts only the layout store (`/api/live-layout?…`, `/api/admin/preview-layout?…`) in production, so a screen cannot be pointed at a document from elsewhere.
- `/api/demo-site-layout?path=demo/sites/…` (the demo recordings) answers only when the server runs with `EVAC_DEMO=1`.
- A site without `data/layouts/<site_id>/index.json` falls back to the agents test fixtures only on a development server.

### Approval gate

`/api/live-layout?site=<id>&bulletin=<id>&shape=<shape>` returns a layout only when the site has auto publish on and the bulletin is approved for that site in `data/approvals.json`; otherwise 403 and the live screen stays ambient with `data-unapproved`. `/admin` previews read `/api/admin/preview-layout` (same parameters), which skips the gate but needs admin access. `POST /api/admin/approve {site_id, bulletin_id, approved, digest?}` binds the approval to the current layout files; with `digest` (what `/admin` showed), it answers 409 when the files changed since. The approval records `mode` (`reviewed` with `digest`, `bulk` without), the credential's `token_label` and the `actor` when one was sent. It also writes the class of the screens (`classes["<site_id>/<hazard>/<template>/<level>"]` in `data/approvals.json`), bound to the layout files without the JMA warning name (the Japanese headline), the source line and the bulletin id, so a later bulletin of the same class with the same wording, translations and arrangement passes the gate once its own report (`data/reports/<site_id>/<bulletin_id>/report.json`) passed a browser or Vision check of every shape and carries the digest of the current layout files (`layout_digest`; an empty `browser_skipped`); revoking a bulletin revokes every class approved from it and the class of its current files. The screens of a drill or test bulletin have a class of their own (`…/drill`, `…/test`, from the layout's `alert.status` or the index row's `status`) that is never approved: they are approved bulletin by bulletin. A synthetic bulletin (`SYN-`, composed by `pnpm -F agents generate`) is approved only for its class: the gate answers 403 `synthetic` for it on `/api/live-layout`, the feed and the replay never show it (`/api/replay` answers no row for a live state that names one), and `POST /api/admin/live` refuses it with 400. `/admin` marks such a bulletin as approved through its class and offers to approve it as a bulletin as well.

### Live state

A site with `replay` plays the recorded bulletins back from a shared start (the demo). Any other site is live: `POST /api/admin/live {site_id, bulletin_id}` (admin access; `bulletin_id: null` clears) writes `data/live/<site_id>.json` `{bulletin_id, fallback_bulletin_id, updated_at}`, moving the bulletin that was live into `fallback_bulletin_id` (`null` clears both), and `pnpm -F agents live --site <id> --bulletin <id>|--clear` writes the same file. The posted bulletin is shown when it is approved for the site and auto publish is on; otherwise the feed and the live screen keep the fallback if that one is approved, and stay ambient if not. A site with `replay` answers 409, and so does a drill or test bulletin (its index row's `status`, else the stored layout's `alert.status` or 【訓練】 headline): those are shown only on a site with `replay`, as the bundled `22424-demo` and `17204-demo` replay the 2016-09-01 tsunami drill, and a live site does not deliver one left in its live state (current or fallback) even when it is approved. A class approval opens a screen only when the bulletin's report holds the `headline_table` check for these layout files and the current table, the stored headlines match `data/jma/`, and the ja_easy table is reviewed (`app/layout/headlineTable.ts`). `pnpm -F agents receive --sites <id>` records the JMA long feeds, composes the screens of each new bulletin that concerns the site and writes this same file; a receiver of your own only calls this endpoint.

### Delivery

- `GET /api/feed/<site_id>`: what the site shows now (`schema/feed.schema.json`), by the replay or the live state above. Only approved bulletins at auto-publish sites become `state: "alert"`. `ETag` / `If-None-Match` → 304. No authentication; CORS open.
- `GET /api/feed?lat=<deg>&lng=<deg>`: the feed of the site nearest the point within 100 m, with the same body, `ETag` and 304 as `GET /api/feed/<site_id>` and `Content-Location: /api/feed/<site_id>`; 404 `no-site-near` without one. Single-facility servers only (see Access).
- `/delivery/<site>/<bulletin>/<shape>.{png,html,json}`: the exported files, served only while the bulletin passes the same gate. A shape without both PNG and HTML is left out of `assets`.
- `POST /api/admin/subscriptions` `{site_id, url, secret}` (admin access, secret ≥ 16 characters): the server checks every subscribed site once a second and posts the feed body when the shown bulletin changes, with `X-EvacLayer-Event: alert|clear`, `X-EvacLayer-Timestamp` (Unix seconds), `X-EvacLayer-Delivery` (a UUID per delivery) and `X-EvacLayer-Signature: sha256=<hex HMAC-SHA256(secret, "<timestamp>.<delivery>.<event>.<raw body>")>`. Receivers should reject a bad signature, a timestamp older than 5 minutes and a delivery id they have already seen (otherwise a captured `clear` could be replayed to take down a live alert); failures are retried 5 times (1, 2, 4, 8, 16 s), a newer state cancels pending retries. Targets must be http(s); addresses that resolve to loopback, private, link-local or other non-public ranges are refused at registration and again at connect time, and redirects are not followed. `NUXT_WEBHOOK_ALLOW_PRIVATE=1` allows LAN targets (demo, local CMS). The last state delivered to each subscription is stored with it, so a change that happened while the server was down (an alert that cleared) is sent after a restart.
- `GET /api/admin/subscriptions?site=<id>` lists registrations without their secrets; `DELETE /api/admin/subscriptions/<id>` removes one (204, or 404).
- Limits: run a single server process (several would each deliver); delivery to `https` targets has not been verified yet (tested over local `http` only).

### Operator notices

The server tells the operator, by Slack (an Incoming Webhook) and by mail, when a warning is out at a live site but not on its screen, when the receiver has stopped receiving JMA bulletins, and when a site's screen has stopped requesting its feed. Both are off until set in the server's environment; a channel that is not set completely sends nothing, and with neither set the server neither checks nor connects anywhere. At start the server logs one line naming the channels that are on (`[notify] channels: slack, mail`, or `none`) and a warning for a setting it cannot use, never a value.

| Variable | Meaning |
|---|---|
| `NUXT_NOTIFY_SLACK_WEBHOOK_URL` | Slack Incoming Webhook URL, https only |
| `NUXT_NOTIFY_SMTP_URL` | the mail server as `smtp://` or `smtps://` URL, with `user:password@` when it asks for them, and without a query |
| `NUXT_NOTIFY_MAIL_FROM` | sender address |
| `NUXT_NOTIFY_MAIL_TO` | recipient addresses, separated by commas |
| `NUXT_NOTIFY_ADMIN_BASE_URL` | the server's URL as the operator opens it (`https://evac.example.org`); notices then link `<base>/admin`, and leave the link out without it |
| `NUXT_NOTIFY_REMIND_MINUTES` | minutes between reminders while the state lasts: default 15, `0` for none, fractions allowed |
| `NUXT_NOTIFY_RECEIVER_STOPPED_MINUTES` | minutes without a successful receive after which a site's receiver counts as stopped: default 30, `0` turns this notice off, fractions allowed |
| `NUXT_NOTIFY_FEED_IDLE_MINUTES` | minutes without a request from a site's screen after which it counts as stopped, and how long a screen must have kept polling to be watched: default 5, `0` turns this notice off, fractions allowed |
| `NUXT_NOTIFY_ALLOW_PLAINTEXT` | `1` lets the Slack URL be plain http and mail go without STARTTLS (tests with local receivers only) |

Mail needs `NUXT_NOTIFY_SMTP_URL`, `NUXT_NOTIFY_MAIL_FROM` and `NUXT_NOTIFY_MAIL_TO` together. `smtps://` is TLS from the start. `smtp://` requires STARTTLS whenever the URL carries a user or password or the server is not on this machine (`localhost`, `127.0.0.0/8`, `::1`), so credentials never go in plaintext; only a relay on this machine without credentials is spoken to in plaintext. Certificates are always checked. A URL with a query turns mail off (with a warning naming the setting), because nodemailer reads options from the query, among them ones that turn the TLS checks off.

Every two seconds the server looks at each site without `replay` and takes at most one bulletin that is out but not on screen, with a reason code:

- the bulletin in the live state (`bulletin_id` in `data/live/<site_id>.json`), when it is a real bulletin (no `SYN-` id, no drill or test) that the gate does not let out: `unapproved` (no approval of the bulletin, and no class approval lets it through), `changed-after-approval` (its screens changed after the approval), `auto-publish-off` (approved, with auto publish off for the site), `screens-missing` (no layout files) or `screens-unreadable` (layout files, or the site's `index.json`, that cannot be read; the issue time and level then read as unknown);
- `check-failed`, before that one: the newest bulletin in the site's `index.json` issued after the live bulletin (after any, when nothing is live) and within the last 24 hours whose screens were composed but did not pass the checks (a row with a `template` and without `screen: true`). `receive` writes such a bulletin into no live state, so the site keeps the older one or nothing.

A notice carries the site id and name, the municipality, the bulletin id, title, issue time and warning level, the reason code with a short explanation, what the site shows now (nothing, or which bulletin) and the admin link, in Japanese and then in English. Text a facility registers or a bulletin brings is folded to NFKC (full-width and compatibility forms become what they look like), control and format characters (line breaks, direction marks, zero-width characters) are taken out, and each field is cut at 200 characters between code points. In Slack each such value is shown as one inline code span, which Slack never turns into a link or a mention: backticks are taken out of the value, `&`, `<` and `>` are escaped, and an empty value is not shown as a span but as a fixed word (`不明` / `unknown`). Mail has no inline code, so in the subject and the body `://` is shown as `[:]//` and the dots of anything that reads as a host name (`evil.example.com`, not `No.3` or `1.5km`) as `[.]`; the subject holds no line break and the body is plain text. In the body of a mail, the recipient's mail program may still turn something in a registered name that looks like a URL into a link. The admin link is the operator's setting and is shown as it is, outside any span.

Each channel sends a notice once per site, bulletin and layout digest. The server keeps what it sent in its memory and in `data/live/<site_id>.notify.json` (when the state was first seen and, per channel, how many notices went out, when the last one did and for which reason), so a restart does not send them again; a record that cannot be written leaves a warning and does not make a notice go out again. A DELETE of the site removes the file, and a site registered again under the id starts with no record. While the state lasts, each channel reminds every `NUXT_NOTIFY_REMIND_MINUTES`, with the number of the notice and the minutes since the state was first seen; a last time that cannot be read, or lies in the future, counts as due. When the reason changes (`unapproved` to `auto-publish-off`, say), each channel says so at once, naming the reason before and after, but never sooner than a minute after its last notice, and not at all when the reason has changed back by then. Notices stop when the bulletin goes out (approved, or let through by its class), another bulletin takes its place, or the site is deleted; no notice says that the state ended. When the same bulletin with the same screens is held back again later (an approval withdrawn), that is a new state: it is notified at once, counted from one. A send that fails is tried again after 2, 5 and 15 seconds; then the server logs a warning with the channel, site, bulletin and an error code, never a URL, address or credential, and tries again after 5 minutes. A send is not tried once the site has been deleted or registered again. Slack posts time out after 10 seconds without traffic and 20 seconds in all, SMTP steps after 15. The channels are independent, sites are checked eight at a time, and the check never holds up the feed or the webhooks. A site whose check fails (a live state that cannot be read) is logged, the same warning at most every ten minutes until it is fixed, and does not hold up the other sites. No API answers the settings or the records: they are for the operator, who reads the notices.

#### Something has stopped

Two more notices say that something has stopped, so that a new warning would not change a screen. Each is one notice that lists every site concerned, never one per site. They go through the same channels, with the same retries, reminders (`NUXT_NOTIFY_REMIND_MINUTES`) and handling of registered text, and are checked on their own timer (a quarter of the shortest of the two thresholds and the reminder interval, between 1 and 15 seconds), apart from the two-second check above.

- When a site joins the list (or, for screens, a listed site should now show a warning), each channel says so at once, never sooner than a minute after its last notice; a site that leaves the list only drops out of the next reminder. The notice stops when the list is empty, and no notice says so.
- A stop that comes back within a reminder interval of its end (15 minutes without reminders) carries on the earlier one, with its count, and is reminded at the interval; one that comes back later is a new notice, counted from one.
- What each channel sent is kept in `data/live/notify/receivers.json` and `data/live/notify/feed-idle.json`, so a restart does not send a notice again. A record whose last notice is older than three reminder intervals (an hour without reminders), left by a server that was down for long, counts as ended. A DELETE of a site takes it out of both records, so a site registered again under the id is told as a new one.

**Receiving stopped.** `receive` writes `received_at` into `data/live/<site_id>.receiver.json` for each site it receives for, after each round in which it fetched every JMA feed. When that time is older than `NUXT_NOTIFY_RECEIVER_STOPPED_MINUTES` for one or more sites without `replay`, the notice lists them with the municipality and the last receive of each. `received_at` is the time the round started and is written once the round has composed the site's screens, so a long round makes it look older by as much; the default of 30 minutes leaves room for that. A site without the record (`receive` never ran for it) is left out silently, so a server that never ran `receive` sends nothing. A record that cannot be read, or whose time is not a time or lies in the future, leaves the site out with a warning in the log, the same warning at most every ten minutes.

**A screen stopped requesting its feed.** Two kinds of request count as the site's screen coming, from the moment the server knows the site exists, whatever the answer (a `304`, or an error while the feed is built): `GET /api/feed/<site_id>`, and the bundled screen's own polling, `GET /api/replay?site=<site_id>` without `municipality` or `t` (which `/screen?mode=live` sends every second for a site without `replay`). The admin previews, the checks and the export open `/screen` with `src=` and send neither, and `/api/live-layout` is not counted, because the export's browser reads it too. A request only sets times in memory, so the answer is not slowed: when a run of requests began, and the last one. The server writes both to `data/live/<site_id>.feed-seen.json`, at most once a minute while requests go on and within a few seconds once they stop, so that a restart knows them. A request after a gap of `NUXT_NOTIFY_FEED_IDLE_MINUTES` or more starts a new run.

A site without `replay` is watched only once one run of its requests has lasted `NUXT_NOTIFY_FEED_IDLE_MINUTES`: a site whose feed was requested once by hand, or never (a screen not installed yet), raises nothing, and a screen back after a long stop is watched again once it has kept polling that long. A watched site whose last request is older than `NUXT_NOTIFY_FEED_IDLE_MINUTES` is listed with when it last came, for how long it has not, and what it should show now (the warning screens with the bulletin id and level, or the ambient screen). This is worked out from the live state and the approval gate alone, without building the feed, at most every 30 seconds for each listed site. Sites that should show a warning come first, and then the notice starts with `【EVAC LAYER・警報中】` and its mail subject with `警報中`. When more than half of the watched sites, and at least three, stop within one check, the notice starts with a line saying so, because then the server's side (a reverse proxy, a certificate, the network) is the likely cause. After a start, and after a check that comes more than 30 seconds late (a clock that jumped, a process that was paused), the server waits `NUXT_NOTIFY_FEED_IDLE_MINUTES` before it decides anything, so screens that were waiting for the server have time to come again. A DELETE of the site removes its `feed-seen.json` and the times in memory. With no channel set, or this notice off, the server keeps no times at all. The feed needs no credentials, so anyone who keeps requesting a site's feed URL makes its screen look alive to this check.

No API answers these records or times.

Not covered: a bulletin that `receive` could not compose at all (an error before any screen was written) leaves nothing on the server and shows only in the receiver's log, a screen that finds its site with `GET /api/feed?lat=&lng=` is not watched, and a site that `receive` never ran for is not in the receiver notice.

### Access

`/api/admin/*` decides what screens may show. Without `NUXT_ADMIN_TOKEN` it answers loopback clients only, and only when Host is localhost/127.0.0.1/[::1], the request is not cross-site, and POST bodies are JSON (403 otherwise). Behind a reverse proxy every request looks like loopback, so set a token there:

```sh
NUXT_ADMIN_TOKEN=<random secret> node app/.output/server/index.mjs
# /admin asks for the token once and keeps it in sessionStorage; API calls send it as a Bearer token
```

Facility tokens let one server serve several facilities. `pnpm -F agents tokens issue --facility <facility id> --label <text> [--expires <ISO 8601>]` prints a token once and keeps only its SHA-256 in `data/tokens.json` (mode 600, gitignored; `list` and `revoke --id <id>` manage it, and the server reads the file on every request, so a revoked token stops at once). A facility token, sent as `Authorization: Bearer <token>`, acts only on sites whose site file carries its `facility_id`; any other site, including one without `facility_id`, answers 404 exactly as a site that does not exist. On the paths it may use it must name the site: `municipality` alone and `GET /api/admin/subscriptions` without `site` answer 400, and `DELETE /api/admin/subscriptions/<id>` of another facility's registration answers 404. Every other `/api/admin/` path, `POST /api/admin/live` among them and any path added later, answers 403 with `data.code: "operator-only"`. An unknown, expired or missing token answers 401, and the loopback rule above is off as soon as `data/tokens.json` holds any token. With facility tokens and no `NUXT_ADMIN_TOKEN` there is no operator credential, so the operator-only paths admit no one. A `data/tokens.json` that cannot be read as a list of token records shuts out every facility token and loopback access alike (logged once); `NUXT_ADMIN_TOKEN` still works, and the CLI refuses to rewrite such a file.

A server with any facility token (or a token ledger it cannot read) holds several facilities, and a facility chooses the coordinates of its own sites, so lookups by place are off there: `GET /api/feed?lat=&lng=` and `GET /api/site-near` answer 404 with `data.code: "place-lookup-disabled"` (`/screen?lat=&lng=` then shows no site; use `site=`), `GET /api/replay?…&reset` no longer restarts a replay, and the public paths (`/api/replay`, `/api/live-layout`) refuse `municipality` without `site` (400), because a facility could add a site to the municipality to change what it names.
